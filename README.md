Итоговую модель дополнительно проверили другими схемами (5 seed): leave-one-day-out 0.886, случайный стратифицированный K-fold 0.882; бутстрэп-интервал 95% по кукам — 0.84–0.91 (раздел «Проверки результата»).

## Как запустить

```bash
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
```

Положить выданные файлы в `data/` (`train.csv`, `test.csv`, `events.csv.gz`), открыть `solution.ipynb` и выполнить Run All. На выходе появится `submission.csv`.

- Python 3.13, зависимости — `requirements.txt` (основные: pandas 3.0, numpy 2.5, scikit-learn 1.9, LightGBM 4.7, CatBoost 1.2, joblib; для запуска ноутбука — Jupyter Notebook). Открыть можно через `jupyter notebook` из venv или в VS Code с ядром из venv. Полный прогон без интерфейса: `jupyter nbconvert --to notebook --execute --inplace --ExecutePreprocessor.timeout=-1 solution.ipynb`.
- Все случайные процессы зафиксированы: `SEED = 0`, `SEEDS = range(10)`, у каждой модели свой `random_state`/`random_seed`. Два прогона дают побитово одинаковый `submission.csv`.
- **Полный прогон** (`RUN_EXPERIMENTS = True`, по умолчанию) пересчитывает весь журнал экспериментов и раздел проверок: ~40 минут на 8 ядрах.
- **Быстрый прогон** (`RUN_EXPERIMENTS = False` в первой ячейке кода) пропускает журнал и проверки и сразу строит `submission.csv` на итоговой конфигурации: ~1 минута. После сохранения сабмита выполнение намеренно останавливается в начале раздела 10 (`SystemExit`). Итоговая конфигурация записана в ноутбуке явно, а в полном прогоне `assert` проверяет, что журнал пришёл именно к ней.
- Обучения внутри одной оценки независимы и идут параллельно через `joblib`; у каждой модели один поток, поэтому результат не зависит от числа процессов.

## Подход

### Данные и очистка

- Признаки считаются только по событиям внутри окна куки: `window_start_ts <= event_ts < window_end_ts`.
- Строки файла событий перемешаны, поэтому события сортируются по куке и времени перед расчётом пауз.
- `platform` записана в разном регистре и с синонимами (`iphone`/`ios`, `desktop`/`web` — одинаковые User-Agent). Значения приведены к трём платформам. Разнобой в написании не связан с классом (есть у 98% людей и почти 100% ботов), поэтому признак из него не строится.
- В файле событий ~1,5% полных дубликатов. Доля дублей среди событий куки у ботов и людей одинаковая (1,44% и 1,34%). То, что хотя бы один дубль чаще встречается у ботов (32% против 20%), объясняется большим числом событий у ботов. Вывод: это шум логирования, дубли удалены, признак из них не строится.
- Пропуски в признаках (например, паузы у куки с одним событием, курсор у мобильной куки) заполняются `-1`, а не `0`, чтобы «данных нет» не выглядело как «пауза 0 секунд».
- Пропуски в самих событиях объясняются типами событий: `search_query`/`search_page` есть только у поиска, `item_id` и `seller_type` — только у событий с объявлением (категория и город заполнены и у поисковой выдачи), `pointer_x/y` — только на web. Доля незаполненных категории и города объявления — отдельный признак (у ботов чаще).
- Категориальные поля (`item_category`, `item_location`, `seller_type`, `search_query`, `event_name`) в модель напрямую не подаются: из них строятся агрегаты по куке — доли, число уникальных значений, энтропия, доля самого частого значения, совпадение категории объявления с категорией поиска. `platform` и `user_agent` разобраны на тип клиента (браузер, приложение, HeadlessChrome, HTTP-библиотека), но эта группа не прошла отбор. Сырые идентификаторы (`cookie_id`, `item_id`) и даты окна признаками не являются.

### Утечки и временное окно

- **События после окна.** Событий до окна нет, а после окна лежит ~12% всех событий (≈41 тыс.). Все `captcha_shown` находятся только после окна: капчу после окна получили 49% ботов и 1% людей. Это реакция антибот-системы, то есть информация из будущего. Остальные события после окна тоже из будущего. Все признаки считаются строго по событиям внутри окна, капча в признаки не попадает.
- **Время создания куки.** Проверено, что у всех кук `cookie_created_at` раньше конца окна, поэтому возраст куки можно использовать как признак.

**Курсор — главная находка.** Координаты курсора есть только на web. У 57% web-ботов курсора нет совсем (у людей — 29%). Но важнее форма облака точек, если курсор есть:

- у людей точки равномерно покрывают экран 1920×1080: нормированный разброс std / (L/√12) ≈ 1 по обеим осям, а отношение std_x/std_y ≈ 1920/1080;
- у ботов — круглое облако ~200 px вокруг точки: разброс по x ≈ 0.37 от равномерного, по y ≈ 0.64, анизотропия `log(std_x/std_y)` ≈ 0 (у людей 0.58);
- облако ботов обрезается краями экрана, поэтому у них встречаются точки ровно на границе (x = 0, y = 0, y = 1080): 3,5% точек против почти нуля у людей.

Похоже, скрипт генерирует координаты «клика» из нормального распределения и обрезает их по экрану. Признаки: нормированный разброс по осям и его z-оценка с учётом числа точек, разброс в пикселях, анизотропия, эксцесс (у равномерного −1.2, у нормального 0), доля и число точек на границе.

**Target encoding объявлений.** Если объявление раньше открывали известные боты, новая кука с этим объявлением тоже, скорее всего, бот. Признаки по объявлениям куки (среднее и максимум): `te_bot_rate` — какая доля всех известных ботов прошлых дней открывала это объявление (на 100 ботов); `te_purity` — сглаженная доля ботов среди размеченных кук, открывавших объявление; `te_seen_bot_share` — доля объявлений куки, которые видел хотя бы один известный бот. Это единственные признаки, использующие метки, поэтому они считаются **внутри модели** (класс `ItemTargetEncoding`): при обучении — только по меткам обучающей части, а для куки с окном в день D — только по меткам кук из дней строго раньше D. Своя метка, метки того же дня и метки проверочной части не используются; на test признак считается по меткам train, то есть только по прошлому. Прирост небольшой (CV +0.003 в пределах шума, rolling +0.011), а на holdout −0.009 — это отмечено в ограничениях. Временная корректность проверена прямым тестом (раздел 10.4a): если перевернуть метки дней ≥ D, признаки кук дней ≤ D не меняются.

**Проверенные группы, не вошедшие в финал** (код есть в ноутбуке, раздел 6.7):
- *Навигация* (19 признаков): глубина листания по каждому запросу, повторы одной выдачи, прыжки через страницы, действия на одно открытое объявление (фото, избранное, контакты), действия по объявлениям без открытия карточки. На базе без контента давала +0.015 CV, поверх контента — ничего.
- *User-Agent и платформа*: тип клиента по самой частой строке UA (браузеры, мобильный браузер, приложение, HeadlessChrome, HTTP-библиотеки), признак автоматизации, платформа. HeadlessChrome у ботов встречается чаще (8% против 2%), но ботов с «обычными» UA намного больше, и поверх поведенческих признаков UA ничего не добавляет. Строку UA ботам легко подделать, поэтому это ожидаемо.

**Признаки по связям между куками и доступность на момент окончания окна.** Популярность и соседи считаются по событиям других кук (и train, и test). Для куки с окном в день D учитываются только куки с окном в день ≤ D: окна — календарные сутки, поэтому все их события произошли раньше конца окна этой куки. Метки при этом не используются. Это проверено прямым тестом (раздел 10.4a): если пересчитать признаки только по кукам до дня D0, значения для этих кук не меняются. Популярность нормирована на число кук тех же дней — это убирает зависимость от числа кук, но не от длины истории: в первые дни train истории мало, и признак там почти всегда нулевой (см. «Проверки результата» и «Ограничения»). Вариант «только последние 7 дней» проверен и оказался хуже всей истории.

Не используются как признаки: сырые `cookie_id`, `item_id`, даты окна (описывают «кто и когда», а не поведение) и события после окна.

### Валидация

Test идёт после train по времени (train — окна 04-06…04-19, test — 04-20…04-26). Сначала валидация была одним временным разрезом: обучение до 04-17, проверка на 04-17…04-19. Оказалось, что в этих трёх днях всего 160 ботов, и P@R0.7 на них очень шумная: бутстрэп-интервал 95% — от 0.26 до 0.60, а смена seed двигает метрику на ±0.02–0.03. На таком шуме нельзя отличить полезный признак от случайности.

Поэтому каждый вариант оценивается тремя схемами:

| Схема | Как устроена | Роль |
|---|---|---|
| **CV по дням** (основная) | 7 фолдов, в каждом 2 дня train целиком; OOF-предсказания всех 11 091 кук, одна P@R0.7 по всем 899 ботам | низкий шум (бутстрэп-интервал 0.40–0.54 против 0.26–0.60 у holdout) |
| **Rolling-origin** | 5 блоков по 2 дня (04-10…04-19), модель учится только на днях **раньше** блока; P@R0.7 по объединённым предсказаниям блоков | проверка при обучении только на прошлом — как у настоящего test |
| **Временной holdout** | обучение до 04-17, проверка на 04-17…04-19 | прежняя схема, оставлена для сравнения |

Куки одного дня никогда не разрываются между обучением и проверкой. Метрика везде считается официальной функцией из `metric.py`.

**Шум от seed и парное сравнение.** LightGBM случайно выбирает строки и признаки для каждого дерева, поэтому один набор признаков на разных seed даёт P@R0.7 с разбросом ~0.01. Каждый вариант обучается на 10 seed, а два варианта сравниваются парно — на одних и тех же seed: средняя разница Δ и t-статистика `t = mean(Δ) / (std(Δ)/√10)`.

**Правило принятия изменения:** метрика значимо растёт хотя бы на одной из двух основных схем — CV по дням или rolling-origin (Δ > 0, t ≥ 2) — и ни на одной из них значимо не падает (Δ < 0, t ≤ −2). Holdout показывается для справки.

Как пришли к этому правилу:
- Сначала решения принимались только по CV. Но возраст куки по CV дал +0.004 (в пределах шума seed), а по rolling-origin — значимые +0.017: изменение полезно для прогноза «на будущее», и правило «решает только CV» его теряло.
- Пробовали вариант, где значимое падение на holdout запрещает изменение. Он отклонял переход RF → LightGBM (CV +0.031, rolling +0.042, holdout −0.043). Но t-статистика по seed учитывает только случайность модели, а не то, что в holdout всего 160 ботов: его бутстрэп-интервал шириной ±0.17 в ~4 раза больше таких разниц. Поэтому holdout в решениях не участвует.

### Модель

CatBoost (1000 деревьев, `learning_rate=0.05`, `depth=6`) поверх 65 признаков и 4 признаков target encoding, которые считаются внутри модели. Итоговый score — среднее предсказаний моделей с 10 seed, обученных на всём train. LightGBM (500 деревьев, `learning_rate=0.03`, `num_leaves=31`, `subsample=0.8`, `colsample_bytree=0.8`) использовался при отборе признаков начиная с шага 6 журнала. Модель выбиралась по небольшому сравнению на той же валидации (таблица «Модель» в разделе «Что ещё пробовали»): гиперпараметры LightGBM оказались близки к оптимуму, CatBoost был лучше на rolling-origin. В журнал вынесены два кандидата — CatBoost и среднее LightGBM + CatBoost; гиперпараметры CatBoost не подбирались.

| Временная корректность (прямые тесты, раздел 10.4a) | признаки по связям между куками, пересчитанные только по окнам до дня D0 (D0 = 3, 9, 13), совпадают с исходными; при перевороте меток дней ≥ D target encoding кук дней ≤ D не меняется | межкуковые признаки не используют будущие дни, target encoding — только метки прошлых дней |
| Adversarial validation (ROC-AUC) | train vs test: 0.997 со всеми признаками, **0.505** без признаков связей между куками; ранний vs поздний train: 0.997 / 0.491 | признаки самой куки не сдвинуты; сдвиг дают только накопленные признаки популярности, и по ним test похож на поздние дни train |
| Абляции групп (LightGBM с теми же признаками и TE, 10 seed) | без курсора CV −0.12; без target encoding rolling −0.011; без долей типов событий CV +0.005; без контента CV −0.005, но rolling +0.009 | курсор — основа решения; результаты по остальным группам смешанные, второй круг отбора на той же валидации не делали |
| Важность признаков (итоговый CatBoost) | паузы и темп (`gap_short_mean`, `gap_short_std`, `sess_rate`, `gin_cv`), форма курсора (`ptr_std_px`, `ptr_spread_z`), повторные просмотры объявлений, разнообразие категорий и городов, возраст куки, target encoding, соседи | ни один признак не забирает больше 6% важности — модель не держится на одном сигнале |
| Порог recall 0.7 на test | отмечено 8,4% кук test против 6,6% train (OOF) | модель на всём train увереннее фолдовых; метрика ранговая, порог подбирает проверяющая система |

### Что ещё пробовали при исследовании признаков

Это результаты исследовательских прогонов: их код не входит в репозиторий, и ноутбук их не воспроизводит (воспроизводится только журнал этапа 2). Перед тем как добавлять группу в ноутбук, каждое семейство признаков исследовалось отдельно: десятки вариантов на общем стенде с той же валидацией (CV по дням + rolling-origin), затем независимая перепроверка на новых seed и проверка кода на утечки. Ниже — варианты, которые **не вошли** в решение. Для ритма и курсора Δ — к базе из 20 признаков первой версии (LightGBM, 3–12 seed); для остальных база указана в таблице.

## Как велась работа

1. Первая версия (этап 1 журнала) — базовые признаки и RandomForest на одном временном holdout.
2. Пересмотр валидации: holdout оказался слишком шумным, введены CV по дням, rolling-origin, 10 seed и парное сравнение; правило принятия изменений формализовано в коде журнала.
3. Исследование признаков по семействам (курсор, ритм, UA, навигация, контент и связи между куками, модели): каждое семейство — десятки вариантов на общем стенде с той же валидацией, затем независимая перепроверка на новых seed, аудит кода на утечки и сравнение распределений train/test.
4. Принятые признаки перенесены в ноутбук; значения функций в ноутбуке сверены с исследовательскими версиями (совпадают побитово). Исследовательский код в репозиторий не входит.
5. Каждая группа признаков добавлялась отдельным шагом: пересчёт всего журнала, выводы в ноутбуке, строка в README, отдельный коммит — в том числе для отклонённых групп.

## Ограничения

- **Мобильные платформы.** На web модель сильная (P@R0.7 ≈ 0.90), на android ≈ 0.49, на iOS ≈ 0.17: у приложений нет курсора, и ботов там ловят только ритм, контент и связи между куками.
- **Накопленная история.** Признаки популярности объявлений и target encoding зависят от того, сколько дней истории накоплено к дню окна. В первые дни train истории мало, на test — больше, чем в любой точке train. По проверкам test похож на поздние дни train, и на них (rolling-origin, holdout) прирост от популярности объявлений и соседей подтверждается, но при сильно другой длине истории поведение признаков может отличаться. Возможное улучшение — не использовать эти признаки (или куки) первых дней, пока история не накопилась.
- **Target encoding** даёт CV +0.003 (в пределах шума) и rolling-origin +0.011, но на holdout −0.009; на test он опирается на метки всех 14 дней train — больше, чем в валидации.
- **Шум оценки.** t-статистика по seed учитывает только случайность модели, а не конечность выборки кук (бутстрэп ±0.035). Небольшие изменения (±0.005) могут не повториться на скрытом тесте; поэтому решения сверялись между схемами, а в конце не делался перебор гиперпараметров.
- **Абляции смешанные** (на LightGBM с теми же признаками): без долей типов событий, возраста куки или ритма внутри сессий правило из раздела «Валидация» приняло бы изменение, а без контента падает CV, но растут rolling-origin и holdout. Второй круг отбора не делали — это ещё одна подгонка под ту же валидацию при эффектах ≤ 0.01; модель, вероятно, можно упростить.
- Оценка на скрытом тесте (0.895) получена одной попыткой; локальные схемы давали 0.87–0.89, то есть расхождения нет. Выбирать модель по ответам платформы не стали — это подгонка под скрытый тест.
